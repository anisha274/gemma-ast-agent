# Localizing Gemma 4 Agents via AST-Guided Retrieval and Self-Correction

*Retrieval finds the bug; test feedback fixes it.*

**Code:** https://github.com/anisha274/gemma-ast-agent (Apache-2.0)

**Runs:** Kaggle notebook *Localizing Gemma 4 Agents via AST-Guided Retrieval*: Version 3 (Gemma 4 E2B) and Version 4 (Gemma 4 E4B)

## Abstract

Small open models can run coding agents on free or local hardware, but their short context makes it hard to show them the right code. We study two inexpensive aids for local Gemma 4 agents. The first is AST-guided retrieval, which ranks individual functions, methods and class outlines (BM25 plus call-graph expansion) instead of whole files. The second is test-driven self-correction, which resets the repository after a failed patch and returns the failing test output together with the code of traceback frames the model had not yet seen. We evaluate on 50 bugs planted in the boltons library and caught by its own test suite, under an identical ~6,000-token context budget. AST retrieval put the buggy function in context for 88% of tasks versus 74% for whole-file retrieval, but did not by itself raise single-attempt fix rates (Gemma 4 E4B: 26% vs 28%). Self-correction did: with the same retrieval, E4B rose from 26% to 42% (exact McNemar p = 0.008), above a single-attempt oracle that is always shown the buggy function (34%). Gemma 4 E2B followed the same pattern at a much lower level (2% to 10%). We release the agent, the bug generator and all run logs.

## 1. Introduction

Coding agents usually rely on large hosted models with long context windows. A developer who wants an agent that runs offline, cheaply, or on private code has to use a small open model instead, and the obvious bottleneck is context: a few thousand tokens cannot hold a repository, so the agent must choose what to show the model.

A common answer is better retrieval. If the model sees the right function, the reasoning goes, it will fix it. We test that assumption directly with Gemma 4 E2B and E4B on Kaggle's free 2× T4 GPUs, comparing whole-file retrieval with structure-aware retrieval at the *same* token budget, and comparing both against an oracle that is always shown the buggy function. We then add a cheap source of extra information that does not depend on retrieval at all: the test suite.

Our contributions:

1. **AST-guided retrieval for small context budgets.** Repositories are indexed into functions, methods, class outlines and module headers, ranked with identifier-aware BM25, boosted by names in the issue and frames in tracebacks, and expanded along the call graph.
2. **Test-driven self-correction with traceback retrieval.** After a failed patch the repository is reset, and the model receives its previous diff, the test output, and the source of repository functions in the traceback that it had not been shown.
3. **A reusable bug-generation and evaluation harness.** It plants single-operator bugs in any pytest-tested Python repository, keeps only those the tests catch, and runs ablations with paired statistics. Every number in this paper is regenerated by one script from the released logs.
4. **An empirical finding.** At this scale, retrieval improves localization but not the fix rate; test feedback is what moves the fix rate.

## 2. System

The agent is about 1,500 lines of dependency-free Python (plus `transformers` for inference). One task runs as: retrieve, generate a patch, apply it, run the tests, and optionally self-correct.

### 2.1 AST index

Every non-test `.py` file is parsed with Python's `ast` module. Each top-level function, method and class becomes a *symbol* with exact line ranges, its docstring, and the set of names it calls. Classes are represented by an *outline* (header, class-level statements, and method signatures), and each module by a *header* (imports and constants), so the model can see structure without whole bodies. Nested functions stay inside their parent.

### 2.2 Retrieval

All retrievers return code chunks and pack them greedily by score into the same budget (about 6,000 tokens, estimated at 4 characters per token), then present them in file order.

- **file (baseline):** BM25 over whole files; the last file is truncated to fit.
- **ast_graph:** BM25 over symbols. Tokenization keeps identifiers and also splits them (`parse_url` gives `parse`, `url`), and symbol names are weighted three times. A symbol gets a bonus if the issue names it, and a larger bonus if it appears in a traceback frame. The top three symbols are then expanded to their callers and callees at half their score.
- **oracle:** the gold (mutated) function first, with the rest filled by `ast_graph`. This is an upper bound on localization, not on repair.

The prompt also lists the repository's file paths (up to 80).

### 2.3 Patch format and application

The model answers with a short root-cause note and one or more SEARCH/REPLACE blocks (the format popularized by the Aider coding assistant). Blocks are applied atomically: an exact unique match first, then a whitespace-insensitive match with re-indentation. Nothing is written if any block fails, edits a test file, escapes the repository, or produces a `SyntaxError`, and each failure is explained back to the model.

### 2.4 Self-correction with traceback retrieval

If the patch applies but tests fail, the agent reverts the repository and sends a new turn containing (a) the previous diff, (b) the last 2,500 characters of test output, and (c) when traceback retrieval is on, up to 1,500 tokens of source for repository symbols that appear in traceback frames and were not shown before. The model writes a complete new patch against the original code. Up to three attempts are allowed. Decoding is greedy (temperature 0) with thinking disabled, so attempt 1 of a self-correcting run is identical to the single-attempt run with the same retriever; our logs confirm this for both models.

## 3. Benchmark

We needed many bugs with known locations in a codebase larger than the context budget, so we built a mutation-based generator in the spirit of mutation testing.

**Repository.** boltons 26.2.0, a pure-Python utility library of about 18,000 lines across many modules, with a fast pytest suite.

**Mutations.** Inside function bodies we apply one operator per bug: comparison flips (`<` to `<=`, `==` to `!=`, ...), arithmetic swaps (`+`/`-`, `//` to `/`), boolean swaps (`and`/`or`), removing `not`, and small integer constants (0, 1, 2 to n+1). Candidates are shuffled with seed 0. A mutant is kept only if the test suite fails without timing out or failing collection, with at most two bugs per function. The first 50 kept (from 1,482 candidates) form the benchmark: 15 constant, 13 arithmetic, 9 comparison, 8 negation and 5 boolean bugs across 17 modules.

**Issue text.** Each issue lists only the failing test names and their short error messages from pytest, so it never reveals the mutation. The gold symbol is the mutated function, which lets us measure localization separately from repair.

**Check.** The generator confirms the clean repository passes before mutating, so reverting a mutation restores a passing state by construction. On the bundled sample library, a harness run that applies each known fix resolves every task, confirming that patch application and scoring work end to end.

## 4. Experimental setup

- **Models:** Gemma 4 E2B-it and E4B-it via Hugging Face `transformers`, float16, split across two T4 GPUs on Kaggle (free tier), greedy decoding, at most 1,024 new tokens per turn.
- **Conditions** (identical context budget):

| Condition | Retrieval | Attempts | Traceback retrieval |
|---|---|---|---|
| file | whole files | 1 | – |
| ast_graph | AST + call graph | 1 | – |
| ast_graph_sc | AST + call graph | 3 | no |
| full | AST + call graph | 3 | yes |
| oracle | gold symbol + AST | 1 | – |

- **Metrics:** *resolved* means the full boltons test suite passes after the final patch. *File hit* and *symbol hit* mean the gold file, or the whole gold function, is in the initial context. We also record tokens and model time.
- **Statistics:** Wilson 95% intervals; exact two-sided McNemar tests on paired tasks.
- **Runtime:** 5.3 h (E2B) and 7.2 h (E4B) of wall-clock on 2× T4 for 250 runs each, including setup.

## 5. Results

**Table 1. Resolve rate on 50 boltons bugs (95% CI).**

| Condition | Gemma 4 E2B | Gemma 4 E4B | Symbol hit | Tokens / task (E4B) |
|---|---|---|---|---|
| file | 4% [1–13] | 28% [17–42] | 74% | 7,765 |
| ast_graph | 2% [0–10] | 26% [16–40] | 88% | 8,561 |
| ast_graph_sc | 8% [3–19] | 38% [26–52] | 88% | 23,112 |
| **full** | **10%** [4–21] | **42%** [29–56] | 88% | 22,952 |
| oracle | 6% [2–16] | 34% [22–48] | 100% | 8,423 |

**Table 2. Paired comparisons, Gemma 4 E4B** ("only A/B" = tasks solved by one condition and not the other).

| Comparison | only A | only B | p |
|---|---|---|---|
| file vs ast_graph | 7 | 6 | 1.00 |
| ast_graph vs ast_graph_sc | 0 | 6 | **0.031** |
| ast_graph vs full | 0 | 8 | **0.008** |
| ast_graph_sc vs full | 1 | 3 | 0.63 |
| oracle vs full | 5 | 9 | 0.42 |
| file vs full | 6 | 13 | 0.17 |

**Finding 1: Structure-aware retrieval localizes better but does not fix more on its own.** At the same budget, ast_graph puts the whole buggy function in context for 88% of tasks versus 74% for whole files (file hit 100% vs 94%). Yet single-attempt fix rates are statistically indistinguishable (E4B 26% vs 28%; E2B 2% vs 4%), and the two conditions solve different tasks (7 vs 6). Even the oracle, which always sees the buggy function, gains only six points over whole files (34% vs 28%, p = 0.61). For a single attempt at this budget, getting the right code into the prompt is not the binding constraint.

**Finding 2: Test-driven self-correction is what moves the fix rate.** With retrieval held fixed, two extra attempts with test feedback raise E4B from 26% to 38% (p = 0.031). Adding traceback retrieval reaches 42% (p = 0.008 vs single-attempt), and no task solved in one attempt was lost. Of the 21 tasks the full system solves, 8 needed a second or third attempt. Traceback retrieval alone adds a net two tasks over plain self-correction, which is too few to separate statistically (p = 0.63).

**Finding 3: Feedback beats perfect localization.** The full system (42%) outperforms the single-attempt oracle (34%). The difference is not significant at n = 50 (p = 0.42), but its direction matches Finding 1: a failing assertion with concrete values tells a small model more than the correct function alone.

**Finding 4: The end-to-end gain over the baseline is real but not yet significant.** Full versus whole-file retrieval is 42% vs 28% (p = 0.17). The whole-file baseline solved six tasks the full system did not, so the choice of retriever changes *which* bugs get fixed more than *how many*.

**Finding 5: Scale shifts the level, not the pattern.** E2B follows the same ordering (full 10% > ast_graph_sc 8% > oracle 6% > file 4% > ast_graph 2%), but with so few successes no E2B difference is significant. Across all conditions E4B solves 31/50 tasks at least once versus 8/50 for E2B, and only one task is solved by E2B and never by E4B.

**Cost.** Self-correction costs about 3× the tokens (22,952 vs 7,765 per task for E4B) and 2.7× the model time (143 s vs 54 s). Because attempt 1 is unchanged, the extra cost is paid only on tasks that would otherwise fail.

## 6. Analysis

**By mutation operator (E4B).** Self-correction gains are concentrated in wrong constants (whole-file 2/15, full 6/15) and arithmetic swaps (3/13 vs 6/13). Comparison flips are the easiest single-attempt category (whole-file 5/9) and do not improve (full 4/9). One plausible reading: a wrong constant or operator rarely looks wrong in isolation, but a failing assertion with the expected and actual values points straight at it. A flipped comparison is either recognized immediately or not at all.

**Unsolved tasks.** 19 of 50 tasks are solved by no E4B condition. Nine of them sit in stateful container and stream classes (`IndexedSet` internals, `BarrelList.iter_slice`, `SpooledStringIO`, `BufferedSocket.recv_until`, `JSONLIterator`), where a single wrong constant or operator changes internal bookkeeping rather than an obvious return value. Neither better retrieval nor three attempts was enough for these.

**A failure pattern: "fixing" toward the bug.** In our harness smoke test on a small sample library, the planted bug changed one comparison in `Rectangle.overlaps` from `<` to `<=`. Both models noticed that the comparisons were inconsistent, then made the *other* comparisons match the bug instead of reverting it: E4B changed all four to `<=`, and E2B rewrote the whole function with the same inverted convention. Small models appear to treat local consistency as a proxy for correctness, which test feedback is well placed to correct.

## 7. Limitations

- **Planted bugs are simpler than real issues.** Each is a single-operator change inside one function, with a test that already fails. The results describe controlled localization and repair, not end-to-end issue resolution.
- **One repository, 50 tasks.** Several differences we report are not statistically significant, and we say so. More repositories and tasks are needed to confirm Findings 3 and 4.
- **Feedback comes from the validation suite.** Self-correction runs the same test command that decides success, as in fail-to-pass setups. The harness supports a separate feedback command per task, which we did not use.
- **Approximate token budget.** Context size uses a 4-characters-per-token estimate, applied identically to every retriever.
- **Two small models, one setting.** Greedy decoding, float16 and a 1,024-token output limit were fixed; other settings may change the absolute numbers.

## 8. Related work

SWE-bench established repository-level issue resolution as a benchmark for language-model agents. Agentless showed that a fixed localize-then-repair pipeline can compete with open-ended agents; our agent follows that structure at a much smaller model scale. Self-Debugging and Reflexion showed that execution feedback and self-reflection improve code generation; we isolate how much of the gain for small models comes from test feedback versus retrieval. Our benchmark construction borrows from mutation testing, and our retriever uses BM25 over syntax-tree units rather than files or fixed-size chunks.

## 9. Reproducibility

Everything runs on free Kaggle GPUs with one notebook (`notebooks/run_kaggle.ipynb`):

1. 15 unit and end-to-end tests run without a GPU.
2. A known-fix harness check must resolve every task.
3. `python -m ast_agent.mutate` rebuilds the 50-task benchmark deterministically (boltons 26.2.0, seed 0).
4. `python -m ast_agent.eval` runs the five conditions. Results append to `results.jsonl` per task, so interrupted runs resume.

`results/kaggle_runs.json` records every task outcome from both runs, and `python results/analyze.py` regenerates every number in this paper. The full per-attempt records, including model responses and patches, are in the Output tab of each Kaggle notebook version.

## 10. Conclusion

For small local Gemma 4 agents with a few thousand tokens of context, structure-aware retrieval reliably gets the buggy code in front of the model, but that alone does not fix more bugs. Running the tests, showing the model what failed, and letting it try again does: E4B went from 26% to 42% on the same tasks with the same retrieval, beating a single-attempt oracle. For builders of offline coding agents, the practical lesson is to spend tokens on a short test-feedback loop before spending them on more retrieved code. Our harness makes it cheap to check whether that lesson holds on other repositories, models and bug types.
